# WP1 Lessons

只追加（OWNERS.json APPEND）。记录可复用的经验：库版本、踩过的坑、被纠正的做法。lead 集成时汇总到 AGENTS.md。


- 步态（`sim/Gait.ts`）跨整数拍的判定两头必须用同一个容差：`cross()` 里 `b <= beat + 1e-9` 让「差 1e-9 就到整数」的拍在这一 tick 落掌，下一 tick 的起点就得是 `floor(prevBeat + 1e-9) + 1`。CORE 版本用 `floor(prevBeat) + 1`，4.8 掌/s 时 288 拍发出 466 次掌根（重复的掌根还会吃掉「干脆」标记）。测试：每拍恰好一次掌根。
- 浮点边界：`0.55 − 0.43 = 0.12000000000000005`，所以「竖直穿透 ≤ 0.12 m 只算绊」必须写成 `pen > grazeY + 1e-9`。凡是规格里写了「≤ / ≥ 某值」的边界，都用精确边界值写一条单元测试。
- 模拟里输入在本 tick 推进之前处理：此刻 `segBeat()` 对应的是 `this.t − TICK_DT`，不是 `this.t`。拿它预测「下一次掌根」要减一个 tick，否则干脆窗口整体偏 8.3 ms。
- 求解器的去重键：只要速度可能因为选择不同而分叉（腿自主抬起时 ×0.85），同一层的节点里程就不同，键里必须带里程；但按 1 mm 取整会让分支永不合并（一个 96 拍的段 87 万节点），按 0.2 m 分桶（节点自身状态仍然精确，只丢掉近似重复的分支）降到 18 万。「让一下」的让开时刻过了之后只记「让开了」，否则每个开口时刻都是一条永不合并的分支。
- 求解器每个节点都要复制一份 `PlayerState`：`Object.assign(new PlayerState(), p)` 占了三成时间，手写 `copyFrom()` 快一倍多；配一条单元测试核对 `copyFrom` 覆盖了全部字段（新加字段忘了写会失败）。热循环里也别每 tick 建闭包：tsx / esbuild 的 keepNames 会给每个闭包调一次 `__name`。
- 检查点之后的 Pace：减速、停拍是临时的，从检查点开始不补放；段中换挡（cadence，5-3「我开始跑」）是持续的，必须按终态补上，否则从换挡之后的检查点重来会回到旧步频。
- 站立段的按步事件（`StepEventDef`，只有 `atStep` 没有 `at`）不进 `CompiledSegment.events`，Sim 直接读 `def.events`；跳过静场时要把还没到的按步事件一起补发，否则必备节拍会丢。
- 跨包的数据问题（例如 §10.1 指派给 WP2 的第一章 R6 间隔）不要为了自己的分支全绿而放松规则：在校验器里加**精确匹配消息**的豁免，降为带说明的 warning，数据一变就自动失效，lead 集成时删除。
- vitest 只按文件并行，同一文件里的用例串行。五章 × 20 个种子的 perfect 扫描按章拆成 `perfect-ch1.test.ts … perfect-ch5.test.ts`，章节还是 null 时只有一个 skip 的用例。测试工具里别用 `until(() => d.of('chapter:end').length)` 这种每 tick 扫全部事件的条件（O(n²)），用 `sim.isEnded`。
- 无头 e2e 很快：`?test=1` 下只在截图帧渲染，第一章 128 s 的游戏时间 1 s 跑完（SwiftShader、640×360、低画质）；渲染每 60 tick 一帧也只要 1–2 s。所以 e2e:chapters 一次取锁跑完五章，远在 10 min 以内。`renderer.info.memory` 只统计上传过 GPU 的几何体，第一遍会随新 chunk 第一次可见而增长；判断泄漏要同一章跑两遍比较第二遍。
- `tsx` 运行 `.mjs` 脚本时可以直接 `import '../src/…/x.ts'`（带扩展名），bot-difficulty 就这样在 Node 里跑模拟，不需要额外的 .ts 入口。
- human 机器人的标定参考（合成的密集跑段，5.4 掌/s、约 50 s、稳度 3、behind）：必需动作 1.3 / 1.7 / 2.0 / 2.5 次每 10 拍 → 失败率约 0% / 3% / 10% / 20%，平均受击 2.5–2.9 次。与 §2.8 的「密度 → 目标失败率」量级一致；第一章的检查点区间在 0%（前四段是 hidden，不会失败）。集成时用 `npm run bot:difficulty -- --trials 60` 看每个区间，超标的区间在报告的 `over` 里。
- 滚动视野的重新规划（机器人每 45 m 续一次）不要在按着 ↓ 的时候做：续规划前要松开 ↓（求解器假定起点没有按键），长桌底下一松手就会撞。等 ↓ 松开再续。
- **更正上面「跨包的数据问题加精确匹配的豁免」那一条**：那是自行降级，被验收员驳回。lead 明确要求某条规则报 error 时，工作包不能自己把它降成 warning，哪怕是为了让自己的分支全绿。照常报 error，在 contract-requests 里写清楚数据、时刻和建议，等 lead 裁定或数据修好。豁免只认 lead 在 DESIGN §10 里的书面批准（`WAIVERS[].approval` 必须逐字出现在 §10，有单元测试）。verify 因此变红时，用 `npm run verify -- --keep-going` 确认其余步骤都绿。
- `__game.events()` 是跨章、跨 start 不清空的环形日志。e2e 判断「本章结束」时只能认本章最后一次 `chapter:start` 之后、`data.id === 本章` 的 `chapter:end`，否则上一章留下的 `chapter:end` 会让下一章 1 帧就「结束」，检查却照样 PASS。这类脚本要带自检：同一章连跑两遍，断言第二遍的 tick 数、帧数和第一遍相同。
- 估算时长不要用常数凑。R10 的「回头后续文字的时长」要按字幕停留公式算（`TEXT`：字数 × 90 ms + 800 ms，和 Game 的字幕队列同一公式），每句只算 0.8 s 掩盖了第一章 1-5 的一处真实违规。凡是规格里引用了别处公式的量，都直接调用同一个函数，并为精确边界写测试：让休息窗终点正好落在最后一个可行输入时刻上报 error，早 0.01 s 就通过。
- `hash()` 手写字段清单一定会漏（翻转、静音、检查点、队列、缓冲……），新字段也会忘。改成按对象自身字段反射递归哈希（`src/sim/stateHash.ts`），只跳过指向只读编译数据的引用和输出缓冲；再配一条测试，逐个改动以前漏掉的字段，断言哈希会变。
- 画面要逐帧采样的查询，例如领跑者的 `Plan.actionAt(s)`，要按区间回答。±0.05 m 的点窗口在 5.4 m/s、30 fps（每帧 0.18 m）下会漏掉动作。
- 静态检查和运行时要用同一个口径。附录 C 允许把必备节拍挂在「窗口」上，校验器就把所有窗口的 id 都算进去了，可 Sim 只在回头开始时标记窗口 id，rest / ask 窗口永远不触发，静态检查和 lint 都显示通过。凡是校验器认定「必定触发」的 id，都要有一条 perfect 跑完后进 `beatsFired` 的单元测试；只在可选操作（按 Q 主动回头）时才触发的，要在静态检查里单独拦下。另外，perfect 自动驾驶会主动回头，所以 perfect 跑不出「非 auto 回头窗口上的必备节拍」这类问题，要靠不按键的 Driver 测试。
- 别的包的数据让自己的分支变红时，除了报 error、写 contract request，最有用的是在 scratchpad 里拿对方分支的最新数据（`git show wp/WP2:path`，只读对象库，不碰对方 worktree）套上自己的校验器复现，找出最小改法并验证余量（把休息窗各放宽 0.3 s、最小间隔加大再解一次）。余量只有几十毫秒的「能过」不算修好。
- 「重来」要回到检查点时的状态。按章累计的标记（例如回头收益「每章第一次」的 `gainUsed`）在到达检查点时记一份，重来时恢复；测试的写法是同一检查点前后各重来一次，断言收益序列。

## 评审修复 U2（2026-10-01）

- 难度机器人不能照搬求解器的路线时刻。求解器在代价相同时总是「最后一刻」换道、贴着下沿伏低，再叠上 ±60 ms 的抖动，就会撞上，超标是假阳性（4-5 @144 20%、5-3 @110 26.7%）。修法分三层：规划时加 0.25 m 余量；给求解器一个可选的代价项 laneLead，让躲避在接触前约 0.3 s 完成，这一项比不在中道的代价大一个量级、比一次输入小得多，所以输入次数不变；横档提前约 0.3 s 按下 ↓，过了横档再松手。改完后所有区间 ≤ 3.3%，换道平均提前 0.58 s。在合成密集段上（5.4 掌/s，每 3–4 拍一行）仍有 5–12% 的失败率，说明机器人还能区分难度。
- 把「提前 / 推迟多少秒」换算成里程，不能乘 `pace.base`。进段第一 tick 它还是 0（「上一 tick 的速度」），以前机器人在段首规划的抖动和提前量因此全部丢了。要从当前 Pace 状态往前推一条名义时间轴（含减速、停拍、换挡），再按时间轴换算。
- 撑跃窗口这类扫描不要用整套 Sim 从某拍开始跑。评审的 jumpall 从 @39 开始扫 2-1 @44，走动的腿在第 0 tick 就撞上玩家，50 次全部绊倒，速度 ×0.7，窗口从 0.225 s 缩成约 0.08 s，报了一个假阳性。按名义时间轴、只对这一个障碍做判定，结果才干净，而且快（全部 192 个 low 障碍只要几十毫秒）。为了保证和 Sim 一致，再用一个合成段逐 tick 实跑对照，误差不超过 1 tick。
- 跳过静场时只保留状态，不把剩下的事件一次全部发出去。节拍 id 照记；follower、flip、leader、noteGet 按顺序应用；hush 只带「自然看完时还剩下的部分」；ambience、atmosphere、fog、rain、hud 只发最后一个，crowd 每组只发最后一个；字幕、音效、机位、替身之类的表现 cue 一律丢掉。测试要先用旧行为（'all'）证明同一个检查确实能抓到问题，免得检查本身是空的。
- 机器人的「失误率」测试样本要够大。MECH_RUN 一趟只有约 12 次输入，4 个种子一共约 48 次，5% 的失误有 8% 的概率一次都不出现。改了 rng 的抽取顺序以后，这个测试就随机地红了。现在用 12 个种子。
- 新加的校验规则如果会对别的单元的数据报 warning，会撞上 `tests/unit/content/chapters.test.ts` 的「五章没有 error，也没有 warning」（`expect(r.issues).toEqual([])`）。R15-jump 对 3-2 的两处报 warning，本分支单独跑 `npm test` 就是红的，数据要等 U1 修。加规则之前先 grep `issues).toEqual([])`，在报告里写清合并顺序（数据修复先合入，或者和规则同一批合入后再跑测试），并用 `git merge-tree --write-tree` 把两个分支合成一棵树、`git archive` 到 scratchpad 里实测。不要为了让测试变绿，把 warning 挪到测试看不见的通道，也不要默认关掉。
- 「平均提前量」会被长样本拉高。回中道时原车道 2–3 s 外还有障碍，也算一次躲避。报告里要同时给中位数、p25 和「< 0.25 s」的比例。laneLead 按 N(0.3, 0.1) 抽，再叠上 ±60 ms 抖动，本来就有约三成落在 0.25 s 以下，所以测试卡「< 0.15 s 的不到两成」，不卡 0.25 s。
- 修好的机器人对密度没有以前敏感。合成密集段（250 拍，5.4 掌/s、步幅 1.1、behind、稳度 3，每 3–8 拍一行随机的 L / H / B）上，最少输入 0.40 / 0.52 / 0.60 / 0.76 / 1.16 次每 10 拍：旧机器人失败率 0 / 2.5 / 10 / 42.5 / 60%（40 次），新机器人 0 / 0 / 0 / 16.7 / 6.7%（120 次）。平均受击次数仍然单调上升（0.49 → 2.73）。新机器人只在个别难的组合上失败。所以五章现在都是 well below target，不说明机器人坏了；用它调谱面密度时，要同时看每个区间的 `meanHits`。
- 核对「跳过和看完，下一段的状态一致」时，界面那一侧的状态也要算进去。Sim 不保存叠加层，所以用界面的纯模型（`src/ui/hud/overlays.ts` 的 `OverlayState`）按 UI 的口径重放 cue 流：`segment` 事件调 `segment(t, cut)`，`overlay` cue 调 `apply`。在全部 15 个静场 / 站立段里，每隔 0.25 s 跳过一次，比较下一段 +0.5 s 和 +2 s 的叠加层。结果是：数据里没有 `clear`，已经开始的 palmHeat / palmNumb / desaturate 都有时长，coldFade 和非全黑的黑场在换段时由 `segment()` 收掉，所以跳过不会留下残影。反方向有差别：静场→静场不算切换（`cut` 只认跑段 ↔ 静场），5-9 在 7.8 s 的 `eyesClosed`（压暗 60%）自然看完时会一直带进 5-10；在约 8.5 s 之前跳过，5-10 就是亮的。章末的 3-10、4-6 跳过时不再淡黑，但结尾卡是不透明的，只差 0.4 s 的淡入。
